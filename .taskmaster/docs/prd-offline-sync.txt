# Overview
VolleyStats records live volleyball matches on a phone or tablet, often in gyms with poor or no network. Live match data is written to a local RxDB database and replicated to Supabase. Today some points, scores and related rows never reach the server, or reach it with different values. The read-only check on 2026-10-07 found 11 of the 96 sets that have points (in 10 matches) with a set score that disagrees with their points.

This project makes offline sync reliable and visible. Every change recorded on a device reaches the server exactly as recorded, through network drops and multi-day offline periods. Users always see whether their data is saved.

# Core Features
- Local edits are never discarded. Root cause: `updated_at` was used as the replication checkpoint while the server trigger rewrote it, so a second update to the same row became a false conflict, and the default handler dropped it. Fix: a server-only `_modified` checkpoint column, `updated_at` kept as the device's edit time, and a conflict handler where the scoring device wins.
- Uploads run from app start, on every screen. Tracked matches are persisted and replicated by the leader tab. A profile refresh no longer cancels match replications. No pause/start loop.
- `pending_changes` records every unsent row (written by collection hooks). It drives the UI and parent-first upload ordering.
- Foreign keys are never an error source. Parent inserts upload first. Errors are classified per row: network, auth and server errors retry forever without counting; permanent errors are rejected with a reason and never block later rows; a missing external reference is named.
- One scoring device per match. A claim RPC records the device, and a server trigger enforces it. A takeover goes through a confirm dialog, online or offline. The previous device becomes read-only and keeps its unsent changes as "superseded".
- A sync badge in the header and on the live page, unsent flags in the match list, a sign-out warning, and a leave-page prompt. Destructive local-data actions are refused while data is unsent.
- A platform adapter (connectivity, foreground, device id, persistent storage), so a later Capacitor/Expo build reuses the sync core.

# User Experience
- Scorer: scores offline without worry. The badge says "N changes saved on this device, will upload when online", then "All saved" and a toast once uploaded, even days later and from any screen.
- Second device (e.g. the scorer's battery died): opening the live match shows "Alex is scoring this match on Chrome · Android (last data received 14:32)" with Take over / Cancel. When offline it asks "Score on this device?".
- Previous device after a takeover: read-only banner. Its unsent changes are shown as "not uploaded", never as an error.
- Problems: "3 changes couldn't be saved" with the reason and a Retry button.

# Technical Architecture
- Supabase migration 20261007000000_sync_reliability.sql:
  - `_modified` column, index and trigger on 12 tables
  - `request_device_id()` reads the `x-device-id` header
  - `update_updated_at_column()` only stamps `now()` on requests without the header
  - `matches.scorer_*` columns, the `claim_match_scorer` / `get_match_scorer` RPCs, and `enforce_match_scorer` triggers
- `lib/rxdb/sync`:
  - `replication.ts`: the adapter, rebased on rxdb/plugins/replication-supabase 17.6.0
  - `match-sync.ts`: 5 replications per tracked match, push modifier per match
  - `reference-sync.ts`: pull-only
  - `manager.ts`
  - `pending-changes.ts`, `dependencies.ts`, `errors.ts`, `conflict-handler.ts`
  - `tracked-matches.ts`, `sync-state.ts`, `scorer-claim.ts`, `status.ts`, `upgrade.ts`
  - `platform/`
- `lib/rxdb/collections.ts`: shared collection setup (browser and tests).
- UI:
  - `components/sync/*`: badge, reason, flag, claim dialog, banner
  - `hooks/use-sync-status.ts`, `hooks/use-unsent-guard.ts`
  - `messages/*/sync.json`: en, fr, es, it, pt
- Tests:
  - Vitest with a fake Supabase server (`tests/unit`) covering every edge case, each ending with server rows = device rows
  - Playwright specs asserting the server matches what the device shows

# Risks and Mitigations
- Old app versions reject unknown columns: Task 1 ships first, and Task 3 asks for confirmation that it is deployed.
- The production database is shared with e2e tests: the migration is backward-compatible (no header means old behaviour), and e2e data is cleaned up by the global teardown.
- RxDB internals (conflict re-push, meta writes): covered by the adapter tests in Task 10. If a test fails, read upstream.js before changing the code.
- Device clock skew affects only the no-known-master conflict path (retry after an interrupted push, or the upgrade). Normal edits are covered by "the scoring device wins".
- Long offline periods: network, auth and server errors never count toward rejection; storage persistence is requested; sign-out keeps the data.
